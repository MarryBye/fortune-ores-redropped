# AGENTS.md

## Project at a glance
- This is a Forge 1.7.10 mod: `FortuneOres`.
- Main entrypoint: `src/main/java/io/github/marrybye/FortuneOres.java` (root package `io.github.marrybye`, mixins in `io.github.marrybye.mixin`).
- The mod id stays `FortuneOres` and the asset domain stays `assets/fortuneores/`; both are baked into existing worlds, so do not rename them along with the package.
- Mod flow is split by lifecycle: `preInit()` creates `Config`, the creative tab, `ItemChunk` and the ore blocks; `init()` resolves which materials the pack has, ore-dicts what survived, resolves the foreign/deepslate blocks and wires `OreSwapper`, the world generator and the ore-gen suppressor; `postInit()` gives late materials a second chance, then rebuilds the chunk names and adds smelting, the drop tables, the machine recipes, the Tinkers' Construct melting recipes and the Thaumcraft aspects.
- Ore behavior is data-driven through `Ore` objects in `FortuneOres.setupOres()` and metadata order matters.

## Build and dev workflow
- Do not edit the root `build.gradle.kts` for normal changes; it only applies `com.gtnewhorizons.gtnhconvention`.
- Put dependency additions in `dependencies.gradle` and repository additions in `repositories.gradle`.
- Use `gradle.properties` for project identity and build flags (`modId`, `modGroup`, `usesMixins`, `accessTransformersFile`, etc.).
- Use `addon.gradle[.kts]`, `addon.late.gradle[.kts]`, or `addon[.late].local.gradle[.kts]` for extra build logic or local-only tweaks.
- First setup / migration: `./gradlew setupDecompWorkspace`.
- Routine validation: `./gradlew build`.
- IDE run target: `./gradlew runClient --username=Developer` (username can be overridden per run).
- CI-style validation mentioned in docs: `./gradlew clean setupCIWorkspace`.

## Mod-specific conventions
- `src/main/resources/mcmod.info` is still used for metadata; keep it aligned with `modId`, `modName`, and `minecraftVersion` when renaming.
- Defaults: every ore ships on as a raw ore (`EnableRawOre`) and off as a generator (`EnableOreGen`), so the pack's own world generation is untouched until a player opts an ore in. `Config` holds no per-ore default lists any more.
- An ore whose material the pack does not provide is dropped entirely, which is what makes "every ore on" cheap. `FortuneOres#hasMaterial` asks the same question `resolveSmeltResult` does - a vanilla ore always passes, everything else needs one of its explicit smelt targets, an ingot, a gem or a dust in the ore dictionary - and `resolveMaterials` runs it in `init` (the ore dictionary is only complete after every mod's pre-init) and again in `postInit` for the mods that register late; a material is never lost once found, so the second pass can only add. `RequireRegisteredMaterial` turns the whole rule off.
- Read `Ore#isActive()` (enabled + material), `Ore#generates()` and `Ore#swapsDrops()`, never the raw `enabled`/`enableOreGen`/`enableRawOre` fields - those are the config's answer, not the game's. `Ore#materialFound` starts optimistically true because the item and the blocks have to be registered in pre-init, before the ore dictionary can answer.
- Nothing an inactive ore owns is registered: no chunk name, icon, ore-dictionary entry, smelting or machine recipe, no creative-tab entry, no drop swap and no world generation. `Ore#usesHost` gates the generated block, its icon and its creative-tab entry per host. `FortuneOres#registerOreBlocks` registers a host/group block only when some enabled ore generates in a dimension that host covers, so an Overworld-only pack never registers the netherrack and end-stone variants, and `OreHost#blockFor` returns null for everything left out - every caller has to check. With every ore off, `preInit` registers no item, block or tab at all and `init`/`postInit` return early. Unregistering a block means an existing save loses the ore blocks already generated with it.
- The deepslate host is only registered when a loaded mod matches the domain of `DeepslateBlockId` (`FortuneOres#deepslateHostAvailable`, checked against `Loader`'s mod list because the block registry is not filled yet in pre-init).
- Ore dictionary registration for the chunks lives in `FortuneOres.registerChunkOreDict`, called from `init` (and again from `postInit` for late materials) and idempotent through `Ore#oreDicted`. It is unconditional for an active ore - a chunk is the ore's raw form whether or not another mod also provides the ore block - and it registers `ore*` under every name and alias, or `dust*` under the same material names when `AllowProcessing` is off. `oreNether*`/`oreDense*` never take a chunk: they mean "this ore, but double". Nothing waits on another mod's registration, so there is no `OreRegisterEvent` listener any more. Register through `FortuneOres.registerOreOnce` rather than `OreDictionary.registerOre` - one name is reached from several places and Forge does not deduplicate.
- `FortuneOres#verifyChunkOreDict` re-reads the ore dictionary after registration and logs a `severe` line for every active chunk missing a name; an ore no other mod can recognise is a silent dead end otherwise. `logMaterialSummary` then says how many ores are active, off, or dropped for lack of a material - that log line is the answer to "where is my ore".
- Both `.lang` files carry exactly the same keys (1 tab + 113 chunks + 448 ore blocks). `ru_RU` block names follow one pattern: the stone host is the plain name ("Медная руда"), and the other hosts prepend "Глубинносланцевая "/"Незеровая "/"Эндовая " and lower-case the first letter. Keep both files in step when adding an ore.
- Every ore must have at least one `Ore#oreNames` entry (`addOreName`), including the `addVanillaOre` ones: those names are what `FortuneOres.addBlockOreDicting()` registers the generated ore blocks under, what the chunk itself is registered under, and what `OreGenSuppressor` matches modded ores by. `addBlockOreDicting` logs a `severe` line for any enabled ore that has none.
- The deepslate host's blocks are additionally registered as `oreDeepslate*` (Et Futurum Requiem's naming) on top of the plain `ore*` name.
- `OreSwapper.OreDictTooltip` lists an item's ore-dictionary names in its advanced tooltip. It fires for *every* item in the pack, not only this mod's, so it is gated behind `OreDictionaryTooltips` and ships off.
- Drop replacement lives in the static `OreSwapper.swapDrops(...)`; silk touch is preserved and XP is spawned from the matched ore entry.
- An ore block is recognised by the mined block itself (instance + metadata), not by what it drops, so ores dropping a finished item (Thaumcraft's amber, Biomes O' Plenty's gems) are swapped too. The table is built from the ore dictionary, `Ore#vanillaBlocks` and `Ore#foreignBlockIds`; matching the dropped stack through the ore dictionary remains a fallback.
- `Ore#foreignBlockIds` holds `"modid:block[:meta]"` ids for ores the ore dictionary cannot describe, resolved in `FortuneOres.resolveForeignBlocks()` as a soft dependency and overridable through the `ForeignOreBlocks` config list.
- What a chunk smelts into is resolved in `FortuneOres.resolveSmeltResult`: the ore's explicit smelt names first, then its name and aliases with the `ingot` > `gem` > `dust` prefixes.
- It has two entry points: the `MixinBlock` injection into `Block#getDrops` (covers machine miners such as Mekanism's Digital Miner, which never fire a harvest event) and `OreSwapper.SwapOres(HarvestDropsEvent)` (fallback for blocks that override `getDrops`, plus the bonus XP). Both are idempotent - whichever runs first wins.
- `allowProcessing` in `Config` changes whether ore chunks are registered as ores or as `dust*` entries.
- Ore-dictionary names may be shared: `addAlias` can hand one ore another's name (Rutile carries `oreTitanium`). `Ore#isAlias` marks those, and `OreSwapper` claims own names before aliases so the ore owning a name keeps the mined blocks registered under it.
- `ItemChunk` expects `nextMeta` and `oreStorage` to stay in sync; add new ores by appending to `setupOres()` rather than reordering existing entries.
- Which dimensions an ore may generate in is `Ore#allowsDimension` (the `SpawnIn*` toggles, or `DimensionIds` as an exact whitelist), read by both the world generator and block registration through `Ore#usesHost` - keep the two in step when adding a host or a dimension switch.
- World-gen shape per ore: height (`OreMinY`/`OreMaxY`, with `NetherMinY`/`EndMinY`/... overrides), `OreVeinSize`, `OreVeinsPerChunk` and `OreVeinChance` - the percentage is the rarity knob, since dozens of ores can be enabled at once and stacking veins per chunk carpets the world. Seed defaults from `OreRarity` and override per ore with `setVeins`/`setVeinChance`/`setBiomes`/`setHarvestLevel`/`setNetherHeight`/`setEndHeight` next to the ore's declaration.
- Biome restrictions are parsed by `BiomeFilter` from each ore's `Biomes` list (`type:MOUNTAIN`, a biome name, `id:35`, `!` to exclude). An ore meant to appear in the End needs `setEndHeight(40, 75)` - the islands float there, so a normal Overworld band never finds end stone.
- Ore aliases are encoded directly in `setupOres()` with extra names like `Aluminium`, `Mythril`, and `Titanium`.
- Item textures live under `src/main/resources/assets/fortuneores/textures/items/` and are named after the ore key in lowercase (or after `Ore#texture` when `setTexture` overrides it); `fallback.png` is the stand-in an ore without its own sprite falls back to.
- Most of those chunk sprites are generated rather than hand-drawn: `tools/chunk_art/` holds a silhouette library (`forms.py`, 16x16 ASCII grids), the per-ore assignment table (`palette.py`, `texture file -> (form, base colour, style, accent)`) and the renderer (`render.py`). Run `python tools/chunk_art/render.py` to rewrite them; `--sheet` also drops a contact sheet next to the repo root for eyeballing the result. The renderer derives the outline from the silhouette, so a form only ever describes shape - add a new ore by adding a form and one `palette.py` line, never by editing pixels. `render.py` warns when two ores end up sharing a silhouette, which is the one rule the set is built on: a chunk has to be recognisable at 16x16 without reading its name, so gems get one cut each, crystals get prisms, metals get lumps and plates, and the Thaumcraft primals get one shape per aspect. A trailing `^` on a form name mirrors it, which is how two related materials stay distinct without a second hand-drawn form.
- The ore *block* textures are a separate pipeline (`tools/build_textures.py` compositing `tools/texture_input/overlays` onto the four host backgrounds) and are not touched by the chunk renderer - redrawing a chunk does not redraw its block.

## Integration notes
- Ore processing lives in `MachineCompat`, called from `postInit` (`TechModIntegration` / `MachineOutputMultiplier` in the config). It registers chunk and ore block -> dust in every supported machine that is installed - Mekanism's Enrichment Chamber, Thermal Expansion's Pulverizer, IC2's Macerator, Immersive Engineering's Crusher - all through reflection plus `Loader.isModLoaded`, so no tech mod is a build dependency. Add a machine by writing another `Machine` implementation with a `create()` that returns null when its mod is absent.
- Those mods only build ore recipes for a hard-coded material list of their own, which is why ore-dicting the blocks as `oreIron` is enough for iron but leaves the other hundred materials unprocessable; `MachineCompat` is what closes that gap. Mods reading ore-dictionary *names* at recipe time (GregTech, and IC2/IE for their own materials) need nothing from us. Ender IO's SAG Mill and AE2's grindstone are still uncovered - both take recipes from their own files rather than an API.
- What a recipe pays out is `MachineCompat#resolveOutput`: `dust*`, then the ore's explicit smelt names, then `gem*`/`crystal*`, and the chunk itself when the pack has none of those. Never `ingot*` - that would skip the smelting step the machines are built around.
- Tinkers' Construct smeltery melting lives in `TinkersCompat`, called from `postInit` (`TinkersSmelteryIntegration` in the config, sharing `MachineOutputMultiplier`). It registers the chunk and all four host blocks as melting inputs for the material's molten fluid. The fluid is resolved out of Forge's `FluidRegistry` under the naming conventions the 1.7.10 ecosystem uses - `<material>.molten`, `molten.<material>`, `molten<material>`, `<material>.liquid`, the bare name - across every one of the ore's smelt bases, so a pack's own molten metals work without this mod knowing they exist. The melting point comes from Tinkers' own `FluidType` table rather than a guess of ours, and an input Tinkers already melts (`getSmelteryResult`) is left alone so its own materials keep their balance. Everything is reflection plus `Loader.isModLoaded`, and the melting method is matched by parameter *shape* rather than an exact signature.
- Thaumcraft aspects live in `ThaumcraftCompat`, also from `postInit` (`ThaumcraftAspectIntegration`). Thaumcraft derives aspects from an item's crafting recipe and a chunk has none, so without this every chunk is aspect-less - unscannable, unusable in a crucible. The aspects are those of what the chunk smelts into (asked of `ThaumcraftCraftingManager.getObjectTags`) plus `terra` for the rock, falling back to `metallum`/`vitreus` when Thaumcraft does not know the material. `FortuneOres#resolveSmeltResult` is package-private for exactly this.
- Both new integrations, like `MachineCompat`, must degrade to a log line rather than a crash: every reflective lookup is wrapped, a missing API disables the integration whole, and neither mod is a build dependency.
- Access transformers are supported via `gradle.properties`, but the README warns they can break source attachment in IntelliJ.
- Mixins are enabled (`usesMixins = true`, `mixinsPackage = mixin`), which makes UniMixins a required runtime dependency. New mixin classes must be listed in `src/main/resources/mixins.fortuneores.json`.
- Foreign ore generation is suppressed in two layers: `OreGenSuppressor.onGenerateMinable` (the ore-gen event) and, when `StrictOreGenSuppression` is on, `MixinWorld` denying the placement outright inside the window that `MixinChunkProviderServer` opens around chunk population. The strict layer only acts during world generation and only when the ore replaces a non-air block.
- If the Forge deobfuscator asks for an MCP conf directory, use `%USERPROFILE%/.gradle/caches/minecraft/net/minecraftforge/forge/1.7.10-10.13.4.1614-1.7.10/unpacked/conf` on Windows.
